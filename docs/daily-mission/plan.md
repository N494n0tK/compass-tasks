# デイリーミッション構想と学習パートナー化ロードマップ

「毎日継続してやること」を **デイリーミッション** として毎日の ToDo に自動で積む仕組みの設計案と、
Compass を勉強のパートナーとして育てるための改善案をまとめる。実装前の構想文書であり、正典仕様ではない。

関連: [../rewrite/app-spec.md](../rewrite/app-spec.md) / [../rewrite/architecture.md](../rewrite/architecture.md) / [../notebook/spec.md](../notebook/spec.md)

---

## 1. 目的

- 「英単語を1セクション」「弱点問題を3問」のような **毎日繰り返す学習** を、毎朝手で追加しなくても今日の ToDo に載せたい。
- 継続できているか（連続日数）が見えるようにして、習慣化のモチベーションにしたい。
- あわせて、Compass が「記録する道具」から「一緒に勉強を回してくれる相棒」に近づくために足りないものを整理する。

## 2. 現状の仕組みと制約（調査結果）

デイリーミッションの設計に効いてくる現状の事実。

### 2.1 今日の ToDo は「保存されるリスト」ではない

- 今日の一覧は毎回 `segs`（計画のミニタスク）・`extras`（単発）・`reviews`（復習）から **導出** される
  （`src/components/parts/ShellTodayItems.ts` の `buildTodayItems` が唯一の入口）。
- 「今日のToDoドキュメント」のような日付単位の保存は存在しない。

### 2.2 繰り返しの概念が存在しない

- `repeat` / `routine` / 習慣 に相当するフィールドはどの型にもない。
- 唯一それらしく振る舞うのは **日付なしの Extra**（`day: ''`）で、毎日表示されるが
  `done` が1個しかないため「1回完了したら永遠に完了」になり、習慣には使えない。

### 2.3 いちばん近い前例は「予習の自動生成」

`src/lib/logic/prepAutogen.ts`（仕様: notebook/spec.md §5）が、デイリーミッションとほぼ同型の問題を既に解いている。

| 論点 | 予習自動生成の答え |
|---|---|
| いつ生成するか | アプリ起動時に1回。クラウド読込完了を待ってから（`CompassApp.tsx` の gate） |
| 何を生成するか | 時間割から翌授業日の科目ぶんの `Extra` を1個ずつ |
| 二重生成の防止 | `prepGenLog`（対象日→生成済みコマ）に記録。**extras の実体は見ない** |
| 削除の尊重 | ログ方式なので「ユーザーが消したタスクが次回起動で復活しない」 |
| undo | `prepGenLog` も UNDO_KEYS に含め、タスクと一緒に巻き戻す |
| ログの肥大化 | 14日より古いエントリを剪定 |

### 2.4 設計を縛る制約

| # | 制約 | 出どころ |
|---|---|---|
| 1 | 永続キーは `PERSISTENT_KEYS` の **末尾にのみ** 追加可（途中挿入は保存判定を壊す） | `src/lib/model/types.ts:305-335` |
| 2 | 「今日」はモジュール読込時に固定。日付が変わっても再読込するまで更新されない | `src/lib/logic/dates.ts:38-41` |
| 3 | 完了は実体ごとの単一 boolean。日付別の完了記録は存在しない | `Extra.done` / `Seg.done` |
| 4 | Firestore 保存は単一ドキュメントの全置換。配列が育つと毎回の保存が育つ | `src/lib/persistence.ts` |
| 5 | 新しいタスク種別を増やすなら `itemOf` / `buildTodayItems` / カウンタを同時に触る必要がある | `ShellTodayItems.ts:10-12` |
| 6 | ノート→復習の連携は外部キーでなく **id の文字列規約**（`nb-{noteId}-{cardId}`）で実現している | `src/lib/logic/noteCards.ts` |

## 3. デイリーミッションの管理方式（提案）

### 3.1 方式の比較

| 案 | 概要 | 評価 |
|---|---|---|
| A. 日付なし Extra を流用 | `day:''` の Extra は毎日出る | × 完了が1回きり。連続日数も取れない |
| B. **ミッション台帳 ＋ 毎日 Extra を自動生成** | 予習自動生成と同型。台帳から今日ぶんの Extra を起動時に作る | ◎ 既存の型・画面・統計がそのまま使える。前例あり |
| C. 新タスク種別 `mission` を追加 | 日付別完了を持つ専用型 | △ 表示・カウンタ・保存の全系統に手が入る。v1 には過剰 |

**案 B を推奨する。** 生成された実体はただの `Extra` なので、ToDo 表示・完了トグル・集中モード・
学習時間の集計（完了 Extra は `buildStudyEntries` が拾う）がすべて無改修で動く。

### 3.2 データ設計（案 B）

```ts
// 台帳（マスタ）。PERSISTENT_KEYS の末尾に追加
export interface Mission {
  id: string;          // 'dm' + base36。生成 Extra の id に埋め込む
  title: string;       // 例: '英単語 DUO 1セクション'
  subj: string;        // 時間割の科目名（色分け・集計に乗る）
  size: SizeKey;       // XS/S/M/L → min は SIZE_MIN から
  dows: number[];      // 実施曜日 0-6。空配列 = 毎日
  active: boolean;     // 一時停止フラグ（テスト期間中だけ止める等）
  createdAt: ISODate;
}
// state.missions: Mission[]
// state.missionGenLog: Record<ISODate, string[]>   // 日付 → 生成済み missionId。14日で剪定
```

生成される Extra は既存型のまま、**id の文字列規約でミッションに紐づける**（制約6のノート方式を踏襲）:

```
id  = 'dm-' + missionId + '-' + YYYYMMDD    // 例: dm-dmx3k2-20260817
day = today
src = 'デイリーミッション'
```

### 3.3 動作規則

1. **生成**: アプリ起動時、クラウド読込完了後に1回（予習自動生成と同じ gate に相乗り）。
   `active` かつ今日の曜日が `dows` に合うミッションについて、`missionGenLog[today]` に無ければ Extra を生成し、ログに記録する。
2. **削除の尊重**: 判定はログのみで行い extras の実体は見ない。ユーザーが今日のミッションを消しても、次回起動で復活しない（予習と同じ設計判断）。
3. **持ち越さない**: やり残した昨日のミッション Extra は `day` が昨日のまま消える（既存の導出ルールどおり）。
   習慣タスクは「今日の分だけ」が正しく、復習のように積み上がらないのがむしろ利点。
4. **完了の記録**: 完了した Extra はそのまま履歴として残り、科目別集計・ヒートマップ・ストリークに自動で乗る。
5. **連続日数**: `id` が `dm-{missionId}-` で始まる完了 Extra から導出する（保存しない）。ToDo カードに 🔥N 日 と表示。
6. **undo**: `missions` と `missionGenLog` を UNDO_KEYS に追加し、生成 Extra と一緒に巻き戻せるようにする（`prepGenLog` と同じ理由）。
7. **当日追加**: ミッションを日中に新規作成したら、曜日が合えばその場で今日ぶんを生成する。

### 3.4 編集 UI

- タスク追加画面（`AddTask.tsx`）の `addType` に **「毎日」** を1個足すのが最小。
  フォームは 単発 とほぼ同じ（タイトル・科目・サイズ）＋ 曜日チェック。
- 同じ画面に登録済みミッションの一覧（active トグル・削除）を置く。
  予習自動生成の ON/OFF（`prepAutoGen`）の隣に並べると設定が1箇所にまとまる。

### 3.5 既知の論点

- **extras の肥大化**（制約4): ミッションは1日数件なので当面は無視できる。
  年単位で気になったら「Nか月より古い完了ミッション Extra を `studyLog` に畳む」掃除を検討する
  （streak の計算根拠が消えるので、畳む際に台帳へ `bestStreak` を書き残す）。
- **日付固定**（制約2): タブを開きっぱなしだと日付が変わってもミッションが積まれない。
  これは予習も同じ既存制限。§4.1 の日付ロールオーバー対応が本命の解決。

### 3.6 段階導入

| 段階 | 内容 |
|---|---|
| v1 | 台帳＋自動生成＋ToDo 表示（src ラベル）。曜日は「毎日」のみ |
| v2 | 曜日指定・active トグル・🔥連続日数表示 |
| v3 | データ画面にミッション継続カレンダー、§4 の弱点ドリル連携 |

## 4. 勉強のパートナーとしての改善案

### 4.1 デイリーミッションと直結するもの

- **日付ロールオーバーの自動化** — 「今日」が起動時に固定される制約(2)を、日付が変わったら
  検知して再計算（もしくは再読込を促すトースト）に変える。毎日開くアプリになるほど効いてくる、地味だが本命の改善。
- **弱点ドリルのミッション化** — 問題抽出（`noteExtract.ts`）には既に「弱い順」ソートがある。
  「弱点問題を3問」というミッションを、抽出結果の上位から自動で中身を差し替えて出せば、
  *何をやるかを考えるコスト* がゼロになる。既存機能の接続だけで作れる、いちばん費用対効果が高い連携。
- **まとめ未記入ノートの提示** — コーネルのまとめ（`summary`）は自分で書く設計（AI は常に空で返す）。
  「まとめが空のノート」は機械的に分かるので、「今日のノートのまとめを書く」をミッションとして自動提案できる。
  書くこと自体が復習になる、という既存設計の思想をそのまま毎日の行動に落とせる。

### 4.2 復習エンジンの強化

- **復習負荷の7日予報** — 復習は今日の負荷にしか乗らない（`loadsMap` の仕様）。`due` は全部持っているので、
  「このままだと木曜に復習が40分たまる」を先に見せて、前倒しを促せる。
- **テスト前ブースト** — 計画（Plan）の `due` とカウントダウンは既にある。テスト1週間前になったら
  該当科目の復習・弱点問題を優先的に今日へ提案するモード。
- **成績との接続** — `scores` は記録されるだけで何にも使われていない。点数が低かった科目の
  復習間隔を詰める・ミッション提案を増やす、まで繋げると記録が行動に還る。

### 4.3 記録と振り返り

- **集中モードの実測記録** — タイマー（15/25/45分）はあるが、実際に集中した時間は `studyLog` に残らない。
  完了時の見積り分数でなく実測を記録できると、データ画面の信頼度が上がる。
- **週次ふりかえり** — 週の復習完了率（`computeWeekRate`）は既にある。月曜の初回起動時に
  「先週: 復習完了率・学習時間・ミッション継続」を1枚のカードで見せて、まとめを書く欄を添える。
  コーネルの「自分で書くことが復習」を週単位に拡張するイメージ。
- **ミッション継続の可視化** — データ画面にミッション別の連続日数・達成率カレンダーを置く（v3）。

### 4.4 将来（制約つき）

- **通知・リマインド** — サーバーサイドが一切ない構成なので、プッシュ通知は PWA 化＋
  ローカル通知が前提になる。優先度は低いが「夜になってもミッションが残っていたら知らせる」は習慣化に効く。
- **GPT 連携の半自動化** — 現状はプロンプトのコピペ運用。ミッションから
  「昨日間違えた問題の類題を作るプロンプト」を生成してコピーできるボタン程度なら、
  API 連携なしで今の運用（外部AIに貼る）のまま実現できる。

## 5. 優先順位の提案

1. **デイリーミッション v1**（§3 案B）— 台帳・自動生成・ToDo 表示。予習自動生成の設計を写せるので実装リスクが小さい。
2. **日付ロールオーバー**（§4.1）— ミッションを「毎日」の名に恥じない挙動にする土台。
3. **ミッション v2**（曜日・連続日数）＋ **弱点ドリル連携** — 習慣化の動機づけと中身の自動化。
4. **復習7日予報・週次ふりかえり** — パートナー感を作る「先読みと振り返り」。
5. その他（テスト前ブースト・成績接続・PWA 通知）は効果を見ながら。
